# Terrain height / elevation — design & scope (#15)

**Status:** scoping (no code yet). **Owner ask (2026-06-18):** "some height in terrain. height minorly
affects train speed / traverse cost etc and adds variety to flat terrain, and allows for realistic rivers
etc." This doc scopes a per-cell **elevation field** and its four effects, grounded in the systems that
already exist, with the determinism plan up front (height feeds hashed cost/speed → a deliberate re-pin).

---

## 1. What exists today (what we're layering onto)

- **Biome cost classes** (`world.rs` ~1190): rail build-cost already scales by biome — `MOUNTAIN 320 /
  HILL 190 / FOREST 140 / PLAIN 100` (×/100), and the hex router's `terrain_cost` swings track around
  water/ridges. So terrain *already* costs differently to cross/build; height refines it with a **continuous
  gradient** rather than a discrete class.
- **Per-span speed** (`line.rs:61` `speed_cap_mm_s`, `speed_cap_at`): every track span already carries a
  speed cap the dispatcher honours — the hook a gradient penalty attaches to.
- **Rivers** (`build_world.py` drainage, render-only): flow-accumulation already draws rivers as cell-centre
  segments; they're **render-only cold water** (never reach the core). Today they're synthesised without a
  real heightmap — height makes them *flow downhill* honestly.
- **3D diorama** (`render/*Mesh.ts` + the deck mesh layers): trees/depots/legions stand on a **flat** ground
  plane today — the "flat terrain" the owner wants variety on.

---

## 2. The elevation field

A per-cell integer **`height`** (decimetres or metres — integer, never float in state), baked into
`CityData` alongside `buildability` (same hex domain), generated by `build_world.py` from coherent noise
(value/Perlin) shaped to the continent (higher inland, a coastal shelf, a mountain spine). Mirrors the
`BuildabilityGrid` shape: `HeightGrid { cell_m, cells: [{x_mm, y_mm, h}] }`. Default empty ⇒ flat ⇒
golden-neutral.

The **gradient** between adjacent cells (Δh / distance) is the load-bearing derived quantity — it's what
costs rail and slows trains, not the absolute height.

---

## 3. The four effects

### A. Traverse / build cost (minor, hashed)
Extend the hex router's per-edge cost with a **gradient term**: crossing from cell A to a higher cell B adds
a cost proportional to the rise (a gentle integer multiplier on top of the biome class — "minorly"). Flat
ground is unchanged (Δh 0 ⇒ no add). This routes rail to *prefer valleys/contours* and pay to climb, giving
the map its read. **Hashed** (it changes `terrain_cost` → the chosen polyline → `capital_cost` + geometry)
⇒ a deliberate re-pin, exactly like the biome multipliers were.

### B. Train speed (minor, hashed — positions move)
A span's `speed_cap_mm_s` gets a **gradient penalty**: a steep span caps lower (a train labours uphill). Keep
it gentle (a small % per unit grade, floored so it never crawls) — "minorly affects speed." **Hashed +
position-affecting** (slower spans change where vehicles are each tick) ⇒ re-pin AND the position
fingerprints move (unlike the capital-only re-pins so far) — call it out clearly in the golden provenance.

### C. 3D relief (render-only — the variety)
Displace the diorama ground + every instanced mesh (trees/depots/legions/stations) by its cell `height` on
the Z axis, so flat terrain becomes rolling hills + a mountain spine. Pure render (the one coordinate
crossing stays `coords/geo.ts`; height is a Z offset in metres). No determinism impact. This is the bulk of
the *visible* "variety" payoff.

### D. Realistic rivers (render-only — the drainage honesty)
Feed the heightmap into `build_world.py`'s flow accumulation so rivers **flow downhill** and **sit in
valleys** (steepest-descent routing on the DEM), widening as they gather flow, meeting the coast at the low
edge. Still render-only (the baked river segments the frontend already draws). Bonus: lakes where flow pools
in a basin.

---

## 4. Determinism plan
- `height` is baked `CityData` (integer), like `buildability` — reconstructible, not hashed itself.
- Effects **A + B feed hashed state** (cost → geometry; speed → positions). The arcadia golden's fixture is
  flat (no height grid) ⇒ **byte-identical**; only a world with a baked height field is affected. When the
  baked continent gets a heightmap, re-pin the arcadia/continent goldens **once** with provenance — and note
  that B moves the **position fingerprint** (a first for this codebase's re-pins; A alone wouldn't).
- Effects **C + D are render-only** (no hash impact); transit + every flat world unchanged.
- Keep the gradient math **integer** (Δh and distances are i64; the penalty is an integer multiplier/divisor
  — no float in `terrain_cost`/`speed_cap`). A property test: a strictly-flatter route is never *more*
  expensive; speed on flat ground equals today's.

## 5. Seams (AGENTS-compliant)
- `CityData` gains `HeightGrid` (default empty) — the only new core input.
- The cost term lives in the existing `terrain_cost`/build-cost path (no new router); the speed term in the
  span `speed_cap` derivation (no new dispatch).
- `build_world.py` gains a `height` generator + DEM-driven drainage; the manifest carries `heightGrid` +
  the (already render-only) rivers, parsed in `sim/city.ts`.
- Render: a Z-displacement in the mesh layers (one helper, `heightAt(cell)`), reused by every instanced mesh.

## 6. Phases (each shippable; flat default keeps it golden-neutral until baked)
1. **T1 — the field**: `HeightGrid` in `CityData` + `build_world.py` heightmap generation (noise → continent
   shape) + parse. No effects yet (data only). Golden-neutral (fixture flat).
2. **T2 — 3D relief (render-only)**: displace the diorama by height — the immediate *visible* variety, zero
   determinism risk. (Do this before the hashed effects: it's the payoff + needs a browser pass.)
3. **T3 — rivers follow height (render-only)**: DEM-driven drainage in `build_world.py`.
4. **T4 — cost + speed (hashed)**: the gradient terms in `terrain_cost` + `speed_cap`; re-pin the
   continent goldens with provenance (note the position-fingerprint move from the speed term). A property
   test for monotonic cost + flat-equals-today.

## 7. Open questions for the owner
1. **How "minor"?** A target like "a 1-in-30 grade costs ~1.5× to build and caps speed ~15% lower" — or
   gentler? (Drives the multiplier constants + the property-test bounds.)
2. **Continuous vs banded height?** A few discrete bands (lowland/hill/highland/peak) read cleaner + re-use
   the biome-class machinery; continuous gives smoother relief + drainage. (Banded is simpler + golden-safe.)
3. **Does very steep gate buildability** (a cliff you *can't* rail, must tunnel/bridge), or only cost more?
   (Ties into the existing water/ridge gate.)
4. **Order:** ship **T2 (3D relief)** first for the visible win, then T3 rivers, then T4 the hashed
   cost/speed? (Recommended — front-loads the payoff, defers the one re-pin.)

**Recommendation:** build **T1 → T2** first (the field + the 3D relief) — it delivers the "variety on flat
terrain" the ask leads with, render-only (no re-pin), and is the satisfying visible change. T3 (rivers) and
T4 (the minor cost/speed effects) follow, with T4 the single deliberate golden re-pin.
